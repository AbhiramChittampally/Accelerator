3. Zero-shot prompting
Zero-shot prompting means asking the model to perform a task without giving it examples of the desired input-output pattern. The model relies on its existing capabilities and the instructions you provide. Week-5 Accelerator-Deep-Learning---Serving---GenAI-LLMs(1).html

Example:
Classify this customer review as Positive, Negative or Neutral.

Review: "The delivery was fast, but the product stopped working."
Return only the label.


Possible response:
Negative


Why might this work well?
- The task is clear.
- The allowed labels are specified.
- The output format is constrained.
- No demonstration examples are required.
When should you use zero-shot prompting?
Use it as your baseline when the task is straightforward or the model already understands the requested format.
Examples include summarizing an article, translating a sentence, explaining an error message or classifying a simple review.
Exam point: zero-shot = no examples supplied in the prompt.
4. Few-shot prompting
Few-shot prompting means including a small number of example input-output pairs in the prompt before asking the model to handle a new input. The examples demonstrate the pattern you want. Week-5 Accelerator-Deep-Learning---Serving---GenAI-LLMs(1).html

Imagine that you want every customer review classified in a particular format.
Without examples, the model may return a label plus an explanation, or use different wording each time. Examples can make the intended pattern more explicit.
Example
Classify each review as Positive, Negative or Neutral.

Example 1
Review: "Excellent quality and fast delivery."
Label: Positive

Example 2
Review: "The item arrived broken."
Label: Negative

Example 3
Review: "The package arrived on Tuesday."
Label: Neutral

Now classify this review:
"The item works well, but delivery was late."

Return only the label.


Possible response:
Positive

5. Chain-of-thought prompting
Your notes introduce chain-of-thought prompting as explicitly asking a model to work through a problem step by step before giving a final answer. Week-5 Accelerator-Deep-Learning---Serving---GenAI-LLMs(1).html

The basic idea is to encourage structured problem-solving instead of asking for an unexplained result.
Consider this arithmetic problem:
A shop has 24 notebooks. It sells 7 in the morning and 5 in the afternoon. How many notebooks remain?

A prompt could be:
Solve the problem below.

Show a concise, numbered calculation.
Then provide the final answer with units.

Problem:
A shop has 24 notebooks. It sells 7 in the morning
and 5 in the afternoon. How many notebooks remain?


A suitable response:
1. Start with 24 notebooks.
2. Total sold: \(7 + 5 = 12\).
3. Remaining: \(24 - 12 = 12\).
Final answer: 12 notebooks.
This format makes the result easier to inspect. For technical tasks, you can similarly request the relevant formula, assumptions, intermediate values and a final result.
A useful distinction: asking for a concise, checkable explanation is not a guarantee that the model's explanation fully reflects its internal computation. For important calculations, independently verify the steps. Also, more reasoning text does not automatically make an answer more accurate.
When is step-by-step prompting useful?
- Multi-step arithmetic and calculations.
- Comparing options against multiple criteria.
- Debugging code through a sequence of checks.
- Planning a process with dependencies.
- Explaining why a particular answer follows from supplied evidence.
For simple tasks, it may add unnecessary length, cost and latency. Choose the level of explanation based on the task.

6. Improve a prompt through iteration
Prompt engineering is not about finding one magical sentence. It is a process of testing and improving instructions.
Suppose you ask an LLM to extract information from an invoice.
Version 1
Prompt: Extract the invoice details.
Problem: it doesn't specify which details or the required format.


Version 2
Prompt: Extract the invoice number, date, supplier and total amount.
Improvement: the required fields are explicit, but the output may still vary.


Version 3
Prompt: Extract the invoice number, date, supplier and total amount. Return valid JSON with exactly these four keys. Use null when a value is missing. Do not infer details that are not present in the invoice.
Improvement: the fields, output structure and missing-value behaviour are specified.


A practical improvement cycle:
1. Write a baseline prompt.
2. Test it with several representative inputs, including difficult cases.
3. Identify the failure: wrong content, inconsistent format, missing fields or unsupported claims.
4. Change the prompt to address that failure.
5. Test again on the same examples and on new examples.
6. Keep the version that performs better against your requirements.









Mistake	Better approach
Giving a vague task	Specify the action and intended outcome.
Forgetting the audience	State the user's experience level.
Providing no output format	Specify JSON, a table, code or another desired structure.
Using contradictory examples	Keep few-shot examples consistent.
Adding too many examples	Use enough examples to establish the pattern without wasting context.
Assuming a detailed explanation is automatically correct	Verify important calculations and factual claims.
Using prompts to solve every problem	Consider retrieval, tools, validation or fine-tuning when appropriate.
Assuming a RAG prompt guarantees grounding	Check whether claims are supported by retrieved passages.
