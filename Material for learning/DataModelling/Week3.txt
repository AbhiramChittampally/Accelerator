WEEK 3 — DATA MODELING: DIMENSIONAL DEEP DIVE
First: the one idea that controls almost everything
Before we touch M1, remember this:
Dimensional modeling is basically organizing business events so that humans can ask analytical questions easily and correctly.

Imagine a supermarket.
Every time somebody buys something:
Customer → buys → Product → at Store → on Date
                         ↓
                    Sales Amount
We want the warehouse to answer:
How much did we sell?
Who bought it?
What did they buy?
Where?
When?
How many?
Which category?
Which region?
So we normally create:
                 DIM_DATE
                     |
                     |
DIM_CUSTOMER — FACT_SALES — DIM_PRODUCT
                     |
                     |
                 DIM_STORE
                     |
                 DIM_EMPLOYEE
                     |
               DIM_PROMOTION
The FACT tells us:
"What happened?"

The DIMENSIONS tell us:
"Who / what / where / when / how?"

M1 — FACT TABLE TYPES
There are three main fact-table types in your syllabus:
1. Transaction Fact
2. Periodic Snapshot Fact
3. Accumulating Snapshot Fact
The easiest way to understand them is:
Type	Think
Transaction	Something happened
Periodic Snapshot	What is the status at regular intervals?
Accumulating Snapshot	How is one process moving through stages?


The source material defines transaction facts at event grain, periodic snapshots at entity × time-period grain, and accumulating snapshots around a process instance that gets updated at milestones. 
M1.1 Transaction Fact Table
Five-year-old explanation
Imagine a shop.
You buy:
Milk
₹50
Then someone else buys:
Bread
₹40
Each purchase is an event.
So we make one row for each event.
FACT_SALES

SALE_ID | PRODUCT | CUSTOMER | AMOUNT
--------------------------------------
1001    | Milk     | A         | 50
1002    | Bread    | B         | 40
That is a transaction fact table.
Grain
The grain could be:
One row per line item on a sales transaction.

This is critically different from:
One row per transaction.

Suppose invoice INV001 contains:
Milk     ₹50
Bread    ₹40
Eggs     ₹100
If your grain is:
one row per line item

you get:
INV001 | Milk  | 50
INV001 | Bread | 40
INV001 | Eggs  | 100
Three rows.
The source's retail example uses exactly this idea: one row per line item on a sales transaction. 
Snowflake example
CREATE OR REPLACE TABLE FACT_SALES_TRANSACTION (
    DATE_KEY INTEGER,
    STORE_KEY INTEGER,
    PRODUCT_KEY INTEGER,
    CUSTOMER_KEY INTEGER,
    TRANSACTION_NUMBER VARCHAR(50),
    QUANTITY_SOLD INTEGER,
    UNIT_PRICE NUMBER(10,2),
    NET_REVENUE NUMBER(12,2)
);
Line by line
CREATE OR REPLACE TABLE
Create the table.
If it already exists, replace it.
FACT_SALES_TRANSACTION
Our fact table.
DATE_KEY INTEGER,
Which date did the sale occur?
This points to:
DIM_DATE
STORE_KEY INTEGER,
Which store?
Points to:
DIM_STORE
PRODUCT_KEY INTEGER,
Which product?
Points to:
DIM_PRODUCT
CUSTOMER_KEY INTEGER,
Which customer?
Points to:
DIM_CUSTOMER
TRANSACTION_NUMBER VARCHAR(50)
This is interesting.
It is not necessarily a foreign key.
We'll come back to this under M4.
QUANTITY_SOLD INTEGER
How many units?
UNIT_PRICE NUMBER(10,2)
Price per unit.
Notice:
100 + 100
doesn't mean anything useful if these are two unit prices.
So this is non-additive.
NET_REVENUE NUMBER(12,2)
Revenue generated by this line.
This is additive.
M1.2 Periodic Snapshot Fact
Now imagine inventory.
You don't necessarily care about every tiny inventory movement.
Instead, every night you ask:
"How much inventory do we have?"

So:
DATE       PRODUCT       STORE       STOCK
------------------------------------------
Aug 1      Milk          Store 1      100
Aug 2      Milk          Store 1       90
Aug 3      Milk          Store 1       75
That's a periodic snapshot.
The source describes this as an entity × time-period grain, such as account × month-end, and specifically uses inventory levels and balances as examples. 
Grain
For example:
One row per product × store × calendar month-end.

So:
20260831 + Store01 + Milk
is one row.
Then:
20260930 + Store01 + Milk
is another row.
Snowflake DDL
CREATE OR REPLACE TABLE FACT_INVENTORY_SNAPSHOT (
    MONTH_END_DATE_KEY INTEGER,
    STORE_KEY INTEGER,
    PRODUCT_KEY INTEGER,
    UNITS_ON_HAND INTEGER,
    UNITS_ON_ORDER INTEGER,
    REORDER_POINT INTEGER
);
Here:
UNITS_ON_HAND
is semi-additive.
Why?
You can do:
Store A + Store B
But you should NOT normally do:
August inventory + September inventory
because those are snapshots at different points in time.
Example
August 31 = 100 units
September 30 = 80 units
Does:
100 + 80 = 180
mean inventory?
No.
Current inventory is:
80
not:
180
This is one of the most important concepts in Week 3.
M1.3 Accumulating Snapshot
Now imagine an online order.
An order goes:
PLACED
   ↓
CONFIRMED
   ↓
SHIPPED
   ↓
DELIVERED
Instead of creating completely independent rows for each stage, an accumulating snapshot can represent the same process instance and update milestone dates.
The source gives order fulfillment as the canonical example. 
Example
ORDER_ID | PLACED | CONFIRMED | SHIPPED | DELIVERED
----------------------------------------------------
1001     | Aug 1  | Aug 1     | Aug 2   | Aug 5
One order.
One row.
As the process moves forward, milestone columns become populated.
Snowflake
CREATE OR REPLACE TABLE FACT_ORDER_FULFILLMENT (
    ORDER_KEY INTEGER,
    CUSTOMER_KEY INTEGER,
    ORDER_PLACED_DATE_KEY INTEGER,
    ORDER_CONFIRMED_DATE_KEY INTEGER,
    SHIPPED_DATE_KEY INTEGER,
    DELIVERED_DATE_KEY INTEGER,
    DAYS_TO_SHIP INTEGER,

);
Initially:
ORDER_KEY = 1001
PLACED = Aug 1
CONFIRMED = NULL
SHIPPED = NULL
DELIVERED = NULL
Later:
CONFIRMED = Aug 1
Later:
SHIPPED = Aug 2
Later:
DELIVERED = Aug 5

Question	Fact type
What sales happened?	Transaction

M2 — ADDITIVE FACTS
Now we move from:
What type of fact table?

to:
How can I mathematically aggregate the measures?

There are three classifications:
ADDITIVE
SEMI-ADDITIVE
NON-ADDITIVE
The course material defines them as:
- additive → can sum anywhere
- semi-additive → can sum across some dimensions but not others
- non-additive → cannot meaningfully sum. DM2(2).pdfPDF
M2.1 Additive
Example:
QUANTITY
REVENUE
COST
DISCOUNT
TAX
If:
Store A = ₹100
Store B = ₹200
Store C = ₹300
Then:
TOTAL = ₹600
You can sum across:
customer
product
store
date
region
provided the measure is genuinely additive over those dimensions.
SQL
SELECT
    SUM(NET_REVENUE) AS TOTAL_REVENUE
FROM FACT_SALES_TRANSACTION;
Easy.
M2.2 Semi-additive
Classic example:
BANK_ACCOUNT_BALANCE
Suppose:
Monday = ₹10,000
Tuesday = ₹12,000
Wednesday = ₹11,000
You don't say:
₹10,000 + ₹12,000 + ₹11,000
= ₹33,000 balance
That's nonsense.
But across different accounts on the same day:
Account A = ₹10,000
Account B = ₹20,000
Account C = ₹30,000
You can say:
Total = ₹60,000
Therefore:
additive across accounts
not additive across time
That's semi-additive.
Correct Snowflake query
SELECT
    STORE_KEY,
    SUM(UNITS_ON_HAND) AS TOTAL_INVENTORY
FROM FACT_INVENTORY_SNAPSHOT
WHERE MONTH_END_DATE_KEY = 20260831
GROUP BY STORE_KEY;
The important thing is:
WHERE MONTH_END_DATE_KEY = 20260831
We're restricting the snapshot to one point in time.
The supplied material explicitly demonstrates this pattern for inventory. 
M2.3 Non-additive
Example:
UNIT_PRICE
MARGIN_PERCENT
CONVERSION_RATE
OCCUPANCY_PERCENTAGE
Suppose:
Product A = ₹100
Product B = ₹200
You don't calculate:
₹100 + ₹200 = ₹300
as "average product price."
Instead:
SUM(NET_REVENUE) / SUM(QUANTITY_SOLD)
The source specifically warns against blindly averaging unit prices and demonstrates a volume-weighted calculation. 
Why this matters in Snowflake + BI
Imagine Power BI/Sigma/Tableau sees:
MARGIN_PERCENT
and blindly does:
SUM(MARGIN_PERCENT)
You could get:
450%
which looks ridiculous.
The database didn't necessarily fail.
The model was wrong.
That's why measure classification is part of data modeling.
M2.4 Golden table
Measure	Type
Quantity	Additive
Revenue	Additive
Discount	Additive
Tax	Additive
Cost	Additive
Inventory	Semi-additive
Account balance	Semi-additive
Unit price	Non-additive
Margin %	Non-additive
Conversion rate	Non-additive


M3 — FACTLESS FACT TABLES
This one initially sounds strange.
"A fact table without facts?"

Exactly.
A factless fact table contains events or coverage information where the existence of a row itself is the information.
The supplied material explicitly divides these into:
1. Event-capturing factless facts
2. Coverage factless facts.
M3.1 Event factless fact
Suppose students attend classes.
STUDENT | DATE | CLASS
----------------------
101     | Aug 1 | SQL
102     | Aug 1 | SQL
103     | Aug 1 | SQL
There may be no:
amount
quantity
revenue
But the row itself says:
Student attended SQL class.

Snowflake
CREATE OR REPLACE TABLE FACT_CLASS_ATTENDANCE (
    DATE_KEY INTEGER,
    STUDENT_KEY INTEGER,
    CLASS_KEY INTEGER
);
Then:
SELECT
    CLASS_KEY,
    COUNT(*) AS ATTENDANCE_COUNT
FROM FACT_CLASS_ATTENDANCE
GROUP BY CLASS_KEY;
COUNT(*) becomes your effective measure.
M3.2 Coverage factless fact
This is even more interesting.
Suppose:
Promotion X
was active
in Store A
for Product Milk
on August 1.
You record:
DATE | STORE | PRODUCT | PROMOTION
-----------------------------------
Aug1 | A     | Milk    | X
Even if:
sales = 0
the row is useful.
Why?
Because now you can ask:
Which promoted products didn't sell?

Without a coverage table, you might only have rows for products that actually sold.
Example
Promotion coverage:
Milk   → promotion active
Bread  → promotion active
Eggs   → promotion active
Sales:
Milk → sold
Bread → sold
Eggs → nothing
The coverage table lets us detect:
Eggs = promoted but zero sales
The supplied material specifically calls this the "killer use case" for coverage factless facts.

T1 — ROLE-PLAYING DIMENSIONS
Imagine:
FACT_ORDER
has:
ORDER_DATE_KEY
SHIP_DATE_KEY
DELIVERY_DATE_KEY
All three refer to the same physical date dimension.
But each has a different meaning.
DIM_DATE
   ↑
   ├── ORDER_DATE
   ├── SHIP_DATE
   └── DELIVERY_DATE
That's a role-playing dimension.
The source explicitly recommends one physical date table with multiple logical roles rather than copying the table. 
Snowflake
Physical table:
CREATE OR REPLACE TABLE DIM_DATE (
    DATE_KEY INTEGER,
    CALENDAR_DATE DATE,
    YEAR INTEGER,
    MONTH_NAME VARCHAR(20)
);
Then:
CREATE OR REPLACE VIEW DIM_ORDER_DATE AS
SELECT *
FROM DIM_DATE;
CREATE OR REPLACE VIEW DIM_SHIP_DATE AS
SELECT *
FROM DIM_DATE;
CREATE OR REPLACE VIEW DIM_DELIVERY_DATE AS
SELECT *
FROM DIM_DATE;
Now your query can do:
SELECT
    ord.YEAR AS ORDER_YEAR,
    shp.MONTH_NAME AS SHIP_MONTH,
    del.CALENDAR_DATE AS DELIVERY_DATE
FROM FACT_ORDER f
JOIN DIM_ORDER_DATE ord
    ON f.ORDER_DATE_KEY = ord.DATE_KEY
LEFT JOIN DIM_SHIP_DATE shp
    ON f.SHIP_DATE_KEY = shp.DATE_KEY
LEFT JOIN DIM_DELIVERY_DATE del
    ON f.DELIVERY_DATE_KEY = del.DATE_KEY;
Why this is powerful
Without role-playing:
DIM_DATE
DIM_ORDER_DATE
DIM_SHIP_DATE
DIM_DELIVERY_DATE
You have duplicated data.
With role-playing:
DIM_DATE
   ↓
3 logical roles
One maintenance point.
The supplied material explicitly calls copying the physical date dimension a modeling mistake. 
T2 — BRIDGE TABLES
Now we encounter:
MANY-TO-MANY
Suppose one bank account has:
Customer A
Customer B
Customer C
and each customer can have many accounts.
You can't simply put:
CUSTOMER_KEY
inside the account fact.
Which customer?
A?
B?
C?
You lose information.
The supplied material explains this exact problem and uses a bridge table with optional weight factors. 
Bridge
FACT_ACCOUNT
      |
      ↓
BRIDGE_ACCOUNT_CUSTOMER
      |
      ↓
DIM_CUSTOMER
Bridge:
ACCOUNT_KEY | CUSTOMER_KEY | WEIGHT
------------------------------------
1001        | 101          | 0.60
1001        | 102          | 0.40
Account balance:
₹100,000
Customer allocation:
Customer 101
₹100,000 × .60
= ₹60,000

Customer 102
₹100,000 × .40
= ₹40,000
Total:
₹100,000
No double counting.
Snowflake
CREATE OR REPLACE TABLE BRIDGE_ACCOUNT_CUSTOMER (
    ACCOUNT_KEY INTEGER,
    CUSTOMER_KEY INTEGER,
    WEIGHT_FACTOR NUMBER(5,4)
);
Query:
SELECT
    CUSTOMER_KEY,
    SUM(BALANCE * WEIGHT_FACTOR) AS ALLOCATED_BALANCE
FROM FACT_ACCOUNT_BALANCE f
JOIN BRIDGE_ACCOUNT_CUSTOMER b
    ON f.ACCOUNT_KEY = b.ACCOUNT_KEY
GROUP BY CUSTOMER_KEY;
Critical rule
Weights should sum to:
1.0
per fact grain.
The supplied material explicitly requires this validation. DM9.pdfPDF

W1 — DATA MARTS
A data mart is a focused analytical area for a business domain.
Imagine a large company:
Enterprise Warehouse
       |
       +---- Sales Mart
       |
       +---- Inventory Mart
       |
       +---- Finance Mart
       |
       +---- Marketing Mart
Sales team doesn't necessarily need every finance table.
So they work with the:
SALES MART
The source describes a data mart as the unit of delivery for a focused business domain. 
Dependent vs Independent
Independent
Sales team creates its own database directly from source.
ERP → SALES MART
Problem:
Finance may do:
ERP → FINANCE MART
and both teams create different versions of:
CUSTOMER
PRODUCT
DATE
Now joining them becomes painful.
Dependent
Instead:
SOURCE
  ↓
ENTERPRISE WAREHOUSE
  ↓
SALES MART
FINANCE MART
INVENTORY MART
This is much more controlled.

H1.1 The three MERGE outcomes
New customer
Not found.
INSERT
Existing customer but changed
Expire old row
+
Insert new row
Existing customer unchanged
Do nothing
The supplied DM11 describes exactly these three outcomes. DM11.pdfPDF
Snowflake implementation pattern
MERGE INTO DIM_CUSTOMER tgt
USING STG_CUSTOMER src
ON tgt.CUSTOMER_ID = src.CUSTOMER_ID
AND tgt.IS_CURRENT = 1

WHEN MATCHED
AND (
       tgt.CUSTOMER_NAME <> src.CUSTOMER_NAME
    OR tgt.REGION <> src.REGION
)
THEN UPDATE SET
    tgt.ROW_END_DATE = CURRENT_DATE() - 1,
    tgt.IS_CURRENT = 0;
Then insert changed/new versions:
INSERT INTO DIM_CUSTOMER (
    CUSTOMER_KEY,
    CUSTOMER_ID,
    CUSTOMER_NAME,
    REGION,
    ROW_START_DATE,
    ROW_END_DATE,
    IS_CURRENT
)
SELECT
    CUSTOMER_SEQ.NEXTVAL,
    src.CUSTOMER_ID,
    src.CUSTOMER_NAME,
    src.REGION,
    CURRENT_DATE(),
    '9999-12-31',
    1
FROM STG_CUSTOMER src
LEFT JOIN DIM_CUSTOMER tgt
    ON tgt.CUSTOMER_ID = src.CUSTOMER_ID
   AND tgt.IS_CURRENT = 1
WHERE tgt.CUSTOMER_ID IS NULL
   OR tgt.REGION <> src.REGION;

H4 — SLOWLY CHANGING FACTS
Important distinction:

UPDATE FACT_SALES
SET NET_REVENUE = 800

Correction:
-1000
+800

= 800

Query 3 — Month-over-month growth
First:
January = ₹100k
February = ₹120k
March = ₹150k
Then:
Feb growth = (120 - 100) / 100
           = 20%

Mar growth = (150 - 120) / 120
           = 25%
SQL:
WITH MONTHLY_REVENUE AS (
    SELECT
        d.YEAR_NUMBER,
        d.MONTH_NUMBER,
        SUM(f.NET_REVENUE) AS REVENUE
    FROM FACT_SALES f
    JOIN DIM_DATE d
        ON f.DATE_KEY = d.DATE_KEY
    GROUP BY
        d.YEAR_NUMBER,
        d.MONTH_NUMBER
)
SELECT
    YEAR_NUMBER,
    MONTH_NUMBER,
    REVENUE,
    LAG(REVENUE) OVER (
        ORDER BY YEAR_NUMBER, MONTH_NUMBER
    ) AS PREVIOUS_REVENUE,
    ROUND(
        100.0 *
        (REVENUE - LAG(REVENUE) OVER (
            ORDER BY YEAR_NUMBER, MONTH_NUMBER
        ))
        /
        NULLIF(
            LAG(REVENUE) OVER (
                ORDER BY YEAR_NUMBER, MONTH_NUMBER
            ), 0
        ),
        2
    ) AS MOM_GROWTH_PCT
FROM MONTHLY_REVENUE;
The course specifically recommends LAG() for prior-period comparisons.

RFM
RFM means:
R = Recency
F = Frequency
M = Monetary
Recency
Question:
How recently did the customer purchase?

Example:
Customer A → yesterday
Customer B → 90 days ago
A is better.
Frequency
How often?
A → 25 transactions
B → 2 transactions
A is better.
Monetary
How much?
A → ₹200,000
B → ₹3,000
A is more valuable.
SQL
SELECT
    CUSTOMER_KEY,
    MAX(DATE_KEY) AS LAST_PURCHASE_DATE,
    COUNT(DISTINCT TRANSACTION_NUMBER) AS FREQUENCY,
    SUM(NET_REVENUE) AS MONETARY
FROM FACT_SALES
WHERE CUSTOMER_KEY <> -1
GROUP BY CUSTOMER_KEY;
